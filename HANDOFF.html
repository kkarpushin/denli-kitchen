Фото и референсы обрабатываются в браузере и не входят в экспорт JSON. Закрытие вкладки удаляет их из текущего сеанса. Схема пока не проверяет окна, двери, коммуникации и конкретные механизмы; финальный проект требует точного замера.

02 / Первый запуск

Локальная работа без сервера приложения.

Нужны Git и Node.js 22 или новее. У самого приложения нет npm-зависимостей, API-ключей или платных сервисов. Доступ к репозиторию настраивает его владелец. Команды выполняются в терминале:

git clone https://github.com/kkarpushin/denli-kitchen.git
cd denli-kitchen
npm start

Откройте http://127.0.0.1:8765/ для прототипа или HANDOFF.html для этого документа. Прямое открытие index.html через file:// не заменяет HTTP-сервер: приложение загружает модули и JSON.

Во втором терминале, из папки проекта:

npm test
npm run build
npm run examples

Для браузерного прогона нужны Python 3.10+ и Playwright/Chromium. Установите зависимости QA по README. Скрипты qa/browser_test.py и qa/browser_provenance.py принимают адрес приложения и путь к браузеру через DENLI_TEST_URL и DENLI_CHROME.

Объём имеющейся проверки. В версии 0.1.1 — 14 синтетических Node-проверок, включая 480 комбинаций планировки и 72 сочетания высоты и стиля, и браузерные сценарии на ширинах 1440, 768, 390 и 320 px. Они проверяют расчётный код и интерфейс. Реальный SketchUp, точность замеров и производственная смета этими проверками не покрываются.

Для ознакомления: пройдите сценарий с ручными размерами, сохраните JSON, затем повторите с фото и эталоном. Сравните происхождение размеров в итоговом документе. Пробный импорт в SketchUp выполняйте по инструкции адаптера.

04 / Практическое продолжение

Четыре проверяемых этапа.

  1. Утвердить один производственный модуль.Конструктор проверяет размеры, материалы, фасады, кромки, зазоры и фурнитуру. Результат: версия каталога и контрольный состав деталей.
  2. Провести один проект через SketchUp.Импортировать JSON в реальном приложении, сверить геометрию и связи деталей, проверить один Undo. Результат: сохранённая модель и протокол расхождений.
  3. Получить и сверить расчёт VIYAR.Начать с одной контрольной детали и четырёх её кромок; затем расширить до проверенной кухни. Результат: импорт, прочитанные обратно данные и цена того же состава.
  4. Измерить качество на реальных помещениях.Собрать контрольные фото, замеры и сметы; сравнить геометрию с эталоном, MoGe-3 и Depth Pro. Результат: ошибки в мм и процентах, доля отказов и доля смет в пределах ±5% на отложенной выборке.

1. Задача проекта

Нужно оценивать размеры помещения по обычной фотографии для предварительного проекта кухни. Для следующего этапа предусмотрены SketchUp и VIYAR PRO. Целевая ошибка сметы не более ±5% требует отдельной проверки. Готовых компонентов и прайсов не было; создан собственный черновой каталог.

2. Что физически можно извлечь из снимка

В модели камеры u = f × X / Z. Замена X → kX и Z → kZ оставляет проекцию той же. Поэтому абсолютный масштаб произвольной сцены не определяется только пикселями: нужны известный размер, метрическое движение/глубина либо предположение о типичных размерах. Это геометрическое рассуждение; нейросеть может дать полезную статистическую оценку масштаба, но не устраняет неоднозначность наблюдения.

Классическая Single View Metrology восстанавливает отношения длин и расстояния между плоскостями при наличии геометрических ограничений, например линии схода плоскости и точки схода другого направления. Авторы сохраняют общий масштабный коэффициент и рассматривают распространение ошибок. Это основа контролируемого измерения, а не подтверждение точного замера любой фотографии. Criminisi, Reid, Zisserman, 2000.

Закрытую шкафом стену невозможно наблюдать на исходном снимке. Достроенный моделью участок должен иметь признак предположения. Дверь, розетка или холодильник не становятся эталоном от распознавания категории: требуется подтверждённый типоразмер/артикул или распределение возможных размеров.

Проверка актуальности и условий использования:

  • MoGe-3: официальный репозиторий сообщает о выпуске 18 августа 2026 года. Код MoGe имеет MIT, включённый DINOv2 Apache 2.0; карточки весов MoGe-2 ViT-L и MoGe-3 ViT-L помечены MIT. Для v3 README указывает зависимость от FlexGEMM/Triton и отсутствие поддержки macOS. Это кандидат для сервера; запуск здесь не проверен. Microsoft MoGe.
  • Depth Pro: README применяет одну лицензию Apple к коду и весам и сообщает, что опубликованная реализация переобучена и не в точности совпадает с моделью статьи. Лицензия разрешает использование и модификацию на оговорённых условиях, без отдельного патентного разрешения. README, лицензия.
  • UniDepth: README указывает CC BY-NC 4.0; нельзя автоматически переносить исследовательский comparator в коммерческий сервис. Репозиторий.
  • DA3: DA3METRIC-LARGE, Base и Small указаны с Apache 2.0; Large, Giant и Nested с CC BY-NC 4.0. Для DA3METRIC-LARGE нужен перевод metric_depth = focal × net_output / 300, где focal в пикселях. Ошибка фокуса переносится в масштаб. Model Cards и FAQ.

Минимальный набор пилота: измерение по плоскому эталону + MoGe-3 + Depth Pro, с MoGe-2 как резервной версией. DA3 добавлять при проверенных intrinsics или в эксперименте с несколькими видами. Это выбор для сравнения, не объявление победителя.

4. Почему маленькая карточка не решает задачу всей кухни

Известный отрезок позволяет масштабировать измерение только при корректных геометрических предпосылках. Для наклонной плоскости требуется проективное выпрямление; четыре угла известного прямоугольника позволяют построить гомографию этой плоскости. Другая стена или передний край столешницы не обязаны подчиняться той же гомографии.

Собственный расчёт чувствительности, не испытание модели: после корректного выпрямления L = R × p_target / p_reference. При ошибке каждого конца отрезка до 2 px ошибка длины может достигать 4 px. Первое приближение относительной ошибки оцифровки: δL/L ≈ 4/p_target + 4/p_reference. Для цели 800 px эталон 40 px даёт примерно 10,5%, эталон 300 px примерно 1,83%. Здесь нет ошибок физического эталона, дисторсии, гомографии, размытия, неплоскостности и экстраполяции. Это не полная верхняя граница ошибки.

Предлагаемый UX: первый снимок принимается свободно. При нехватке данных предложить приложить к нужной стене большой плоский предмет известного размера и переснять так, чтобы были видны четыре угла. Пользователю не требуется обмерять комнату рулеткой. Печатный шаблон допустим с проверкой фактического масштаба печати. Для старого снимка возможен подтверждённый артикул объекта, с учётом плоскости его границ.

LiDAR остаётся необязательным улучшенным путём. Apple описывает RoomPlan как Swift API на базе камеры и LiDAR iPhone/iPad, с параметрической моделью и экспортом USD/USDZ. Открытая страница не устанавливает миллиметровую гарантию для изготовления кухни. Это отдельный мобильный путь, не функция загрузки JPEG. Apple RoomPlan.

Идеи «эталон в кадре», «стандартный предмет», «интерактивная линейка» и «масштаб по распознанным объектам» уже описаны. Общую идею нельзя объявлять уникальной. Нельзя и заключать, что любая реализация нарушает эти патенты: требуется сравнение всей совокупности признаков конкретной реализации, действующих требований и территорий.

Собственный задел DENLI разумно искать в связке: выбор минимального дополнительного снимка, распространение неопределённости до модулей и цены, каталог проверенных динамических компонентов, производственный регламент и данные о расхождениях с контрольными замерами. Новизна этой связки пока не установлена. Её практическая защищённость может опираться на производственные данные и процесс независимо от будущего патента.

6. Предлагаемый технический конвейер

Это проектное решение для полного сервиса. Локальный прототип уже реализует отдельные части, включая разметку фото, геометрическую оценку и черновой расчёт по собственному каталогу; полный конвейер с моделями и поставщиком пока не реализован и не проверен.

  1. Приём. Сохранять исходник и EXIF, отдельно фиксировать преобразования. Проверять ориентацию, размытие, засветку и видимость углов. Не подменять измерительный исходник генеративно улучшенной картинкой.
  2. Разбор видимого. Сегментировать стены, пол, проёмы и препятствия. Разделять видимые границы и достроенные гипотезы; фото помещения и стилевые референсы.
  3. Геометрия. Оценить глубину и камеру двумя моделями, найти плоскости и линии схода. Прямоугольность помещения проверять. Согласие моделей не доказывает точность: ошибки могут быть общими.
  4. Масштаб. Приоритет у подтверждённого эталона/замера. Плоскостное измерение применять только к подходящей поверхности. Предположения о мебели хранить с диапазоном.
  5. Следующее действие. Возмущать координаты точек, масштаб и параметры камеры; оценивать чувствительность. Если неопределённость меняет состав кухни, запросить конкретный снимок или эталон нужного места. Перемещение камеры полезнее дубликата из той же точки.
  6. Каталог. Размещать разрешённые DENLI модули, зазоры и зоны открывания по их правилам. Рендер не является источником спецификации деталей.
  7. Смета. По допустимым сценариям пересчитать модули, материалы, кромки, фурнитуру, труд, доставку и монтаж по одному прайсу. Если на границе размеров меняется состав, показать варианты или уточнить данные.
  8. Экспорт. Передавать параметрическую спецификацию адаптерам SketchUp/сметы. До контрольного замера помечать предварительной; картинка не должна автоматически становиться производственным заданием.

Минимальный контракт измерения:

{
  "dimension": "wall_a_visible_span",
  "unit": "mm",
  "value": null,
  "interval": null,
  "method": "unscaled_photo",
  "scale_source": null,
  "plane_id": "wall_a",
  "evidence": ["photo_001"],
  "assumptions": [],
  "status": "needs_scale",
  "production_ready": false
}

null означает отсутствие данных. Для модельного результата нужен статус estimated, для геометрии с эталоном reference_calibrated; ни один автоматически не означает готовность к производству. Численный интервал можно подписывать вероятностью покрытия только после эмпирической калибровки.

7. Как проверить ±5%

Размеры и стоимость оцениваются отдельно. Пять процентов стены 3 м составляют 150 мм: это арифметический пример, не монтажный допуск. Ошибка длины не равна ошибке цены: зазор может заменить целый модуль; материал или механизм меняет цену без изменения размеров.

Предлагаемый стартовый эксперимент:

  • Собрать ориентировочно 30–50 реальных помещений с разрешением на снимки, контрольным замером и спецификацией. Это инженерный пилот, недостаточный для безусловной рыночной гарантии.
  • На каждом получить первый обычный снимок, фото с плоским эталоном, несколько видов, при доступности LiDAR. Включить реальные мессенджерные копии, размытие, тёмные участки, отражающие фасады, перекрытые углы, узкие комнаты. Искусственные ухудшения считать отдельным stress test.
  • Разделять калибровку и проверку по помещениям, не по фотографиям одной комнаты. Не подгонять правила отказа по финальной группе.
  • По размерам измерять ошибку в мм и процентах, медиану/P95, покрытие интервалов, долю отказов, число дополнительных действий. Разделять видимые и восстановленные участки, качество и наличие масштаба.
  • По смете считать abs(preliminary − control) / control при одинаковых материалах, комплектации, дате прайса и услугах. Изменённый заказ не является контрольной сметой исходного. Учитывать все выданные предложения, не только удачные.
  • Цель пилота: установить входные условия, при которых система укладывается в ±5% стоимости, и долю подходящих обращений. По геометрии DENLI должен задать отдельные допуски стен, проёмов, зазоров и коммуникаций.

Метрики научных benchmarks глубины не заменяют эту проверку: средняя ошибка пикселей и доля пикселей под относительным порогом не являются гарантией ширины стены или цены.

8. Следующий шаг и недостающие входы

В локальном прототипе создан стартовый каталог, явно помеченный invented-starter-catalog, validated: false, manufacturingReady: false. Реализованы геометрическая оценка по эталону и различение демонстрационных, ручных и полученных из фото размеров. Эти функции ещё не доказывают точность на реальных кухнях. Следующий исследовательский шаг: расширить происхождение измерений до плоскостей и калиброванных интервалов, затем сравнить MoGe-3 и Depth Pro с геометрическим baseline на одних контрольных помещениях.

Отсутствие готового каталога больше не препятствует развитию прототипа: пользователь разрешил создать его самостоятельно. Для проверки производственной пригодности всё ещё нужны контрольные фото и замеры DENLI, проверка придуманных модулей и правил конструктором, действующие цены и успешно сверенный обмен со SketchUp и VIYAR PRO. Готовыми результатами исследования являются этот обзор, кандидаты, карта патентных пересечений и проверяемый план эксперимента; собственный стартовый каталог и приложение являются отдельными артефактами продуктовой ветки.

Контракт производственной детали

Хранить part_id, module_id, количество, толщину, материал/SKU, текстуру, локальные оси, габаритные и пильные размеры, четыре кромки, сверления/пазы/вырезы и происхождение параметров. Различать none и unknown; неизвестная кромка не равна отсутствующей. Стороны определять относительно локальных осей, не относительно экрана после поворота шкафа.

CSV-документация называет размеры пильными, но также предлагает шаблоны габаритных размеров и преобразования между ними. Выбранный режим необходимо проверить на контрольной детали с известной кромкой, исключив двойное вычитание толщины. Для каждого материала и толщины нужен отдельный пакет, если режим импорта не сохраняет их построчно. Пример ниже документирует колонки, но не заявляет проверку импорта. CSV

Площадь плит и сумма периметров не определяют стоимость раскроя: нужны размеры листа, направление текстуры, рез, обрезка краёв, остатки, минимальные размеры и дополнительные операции. Эти ограничения должны быть версионированными данными поставщика. Производственные ограничения

Предлагаемая цепочка

  1. Фото, референсы и комплектация; у размеров есть источник и неопределённость.
  2. Детерминированный план модулей и проверки проходов, открывания, воды, вентиляции, техники и стыков. Новый тип остаётся черновиком до проверки конструктора.
  3. SketchUp-модель той же ревизии плана. Адаптер sketchup/denli_draft.rb создаёт обычные параметрические компоненты и сохраняет атрибуты. Это не настоящие Dynamic Components с формулами.
  4. Каноническая деталировка → проверенный ABF/DXF либо ограниченный CSV → сравнение прочитанных обратно деталей и обработок. Хранить исходник, экспорт, версии и хеши.
  5. Расчёт VIYAR + не вошедшие позиции фасадов/столешниц/фурнитуры + работы, доставка, монтаж, налоги и маржа DENLI. Исключить двойной учёт. Фиксировать дату цен, валюту, скидку аккаунта и состав предложения.
  6. Клиент получает визуализацию, состав и честный диапазон. Производственный заказ и оплата остаются отдельными действиями после проверки.

Состояния: draft → model_built → parts_validated → supplier_imported → supplier_reconciled → quoted; отдельно needs_review и failed. Переход подтверждается артефактом. Повтор одной ревизии не создаёт повторный заказ; quoted обозначает предварительное предложение.

Проверка цели ±5%

Сравнивать одинаковый состав кухни, цены на одну дату, одинаковые налоги, доставку и монтаж. Ошибка проекта: abs(estimate - reference) / reference. Отдельно измерять влияние исходного фото, выбора комплектации и производственной калькуляции; изменения пожеланий клиента учитывать отдельно.

Разделить реальные завершённые проекты на настройку и отложенную проверку. Показать размер выборки, медиану, 95-й процентиль, максимум, долю случаев в ±5% и долю проектов, отправленных на ручной разбор. Требование «максимум 5%» не выполняется средней ошибкой 5%. До проверки цель не достигнута; диапазон в прототипе не является статистической гарантией.

Трудность копирования создаётся проверенным каталогом, правилами, историей фактических смет и исполнением. Библиотеку, деталировку и цены держать на сервере, клиенту отдавать нужный результат; доступ и частоту запросов ограничивать. Это не делает идею некопируемой. Локальный прототип с JS-правилами такой защиты пока не имеет.

Артефакты и доступ для следующего этапа

Нужны проверка черновых модулей конструктором, рабочая станция SketchUp с нужными расширениями и лицензией, тестовый аккаунт VIYAR с материалами/скидками, успешно импортированный пример со сметой и исторические проекты для калибровки. Режим unattended/виртуализации и совместимость проверяются отдельно. Для партнёрского API нужны его документация и предоставленные поставщиком права.
